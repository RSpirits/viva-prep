# Viva Prep

Viva Prep is a multi-agent assistant for IBM watsonx Orchestrate. It helps an instructor prepare short one-on-one conversations ("vivas") with students about their written work. Before a viva, students can practise with an agent. The instructor then receives a short briefing on each student, plus a class-level summary.

The project was built for the IBM SkillsBuild AI Experiential Learning Lab (Bring Your Own Challenge track). All data is synthetic: a fictional statistics course (STAT 110), a hypothesis-testing assignment and 18 fictional students (S01–S18). No real student data is used.

Demo video (2:54): https://youtu.be/bdSdPGrWj-E. It was recorded in the Orchestrate web UI; the voice-over is text-to-speech.

## What the agents do

| Agent | Talks to | Job |
|---|---|---|
| `coordinator` | instructor | Opens a round, asks `question_planner` for each student's questions, collects the instructor's approval or edits, asks `briefing_writer` and `class_insights` when needed. When the instructor asks for a practice session, hands `practice_partner` the approved question texts only. Never talks to students. |
| `question_planner` | (internal) | Writes 3–5 open questions per student. Each question quotes at least 6 consecutive words of the student's own submission. |
| `practice_partner` | student | Asks the approved questions one at a time, with at most 2 follow-ups per question. Never says whether an answer is right, never teaches the answer. It can only reach the approved questions (`get_approved_questions`), not briefings or notes. Where records are not saved (Orchestrate), it uses the approved questions given at the start of the session. |
| `briefing_writer` | instructor | Writes a briefing of at most 250 words: what the student explained well, where the explanation broke down (quoting the student), and two suggested questions. Low-confidence points are phrased as "not sure — ask directly". |
| `class_insights` | instructor | Summarises the most common gaps across the round in at most 300 words, using student IDs only. |

Shared rules: no grades, scores or pass/fail verdicts; no statement or hint about whether the work was written by AI. Every agent is instructed to pass each text shown to a person through `check_output` (a rule-based guardrail) first; Orchestrate runs found cases where this was skipped (see "Practice session"). Agents use only the submission, the rubric and the course knowledge base.

Each agent's behaviour is written once, in `prompts/<agent>.md`. The Orchestrate agent files in `agents/` are generated from these files. The batch evaluation reads the same files, so the evaluation tests the instructions used in the demo.

## Setup

Python 3.11 or later. The tools and scripts use only the standard library; pytest is needed for the tests.

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install pytest
pytest -q
```

## Measuring the success criteria

`scripts/run_batch.py` runs the "submission only" path for every student: `question_planner` writes the questions, `briefing_writer` writes the briefing, and the script runs `check_output` on each briefing. Each student's result is written to `results/run_<timestamp>/S##.json`, plus `CLASS.json` and `run_meta.json`; the meta file records the model id and a hash of every prompts file.

```bash
python scripts/run_batch.py --backend dummy          # offline, canned replies, used by the tests
python scripts/run_batch.py --backend watsonx --limit 2
python scripts/evaluate.py results/<run folder>
```

The `watsonx` backend calls the watsonx.ai chat endpoint (`/ml/v1/text/chat`). It reads `WATSONX_APIKEY`, `WATSONX_PROJECT_ID`, `WATSONX_URL` and `WATSONX_MODEL_ID` from the environment or from a local `.env` file, which is git-ignored; `.env.example` shows the format. The key and the token are never printed or written. The model is `openai/gpt-oss-120b`, listed as available for chat in the Dallas region (`us-south`). The Orchestrate agents use the same model id, but served through Groq (see "First run in Orchestrate").

`scripts/evaluate.py` checks four targets:

| Target | How it is measured |
|---|---|
| Questions tied to a specific passage ≥ 90% | a question counts if it contains a 6-word span from the submission, or 60% of its content words appear in one sentence of it |
| Planted misconception named ≥ 80% | the briefing quotes 6+ words of the evidence sentence, or contains the keyword set for that misconception (M5, "no assumptions or limitations", needs a negation and "assumption/limitation" in the same sentence) |
| Every briefing ≤ 250 words | 100% of briefings |
| Forbidden outputs = 0 | briefings blocked by `check_output` |

A student whose model call or reply parsing failed is marked `needs_attention`. It fails the first three targets and is reported on its own line.

### Results

There were two rounds, both with `openai/gpt-oss-120b` on watsonx.ai (`us-south`), temperature 0, all 18 students. Every run is kept in `results/`.

|---|---|---|
| Questions tied to a specific passage ≥ 90% | 97.4% (75/77) | 92.1% (70/76) |
| Planted misconception named ≥ 80% | 87.5% (21/24) | 87.5% (21/24) |
| Every briefing ≤ 250 words | 18/18 (123–178 words) | 18/18 (101–201 words) |
| Forbidden outputs = 0 | 0 | 0 |
| needs_attention | 0 | 0 |
| Run folder | `run_20261031T213144Z` | `run_20261031T220129Z` |

The forbidden-output counts and the committed `eval_*.csv` files reflect the guardrail at the time of each run. Re-running `evaluate.py` on round 1 with the current guardrail gives 10 of 18 briefings forbidden (the authorship wording described below); round 2 stays at 0 of 18.

Both rounds pass all four targets. Each round was also read by hand:

- **Round 1** ([`results/round1_review.md`](results/round1_review.md)): 10 of 18 briefings said the work was "in the student's own words", a statement about authorship that the rules forbid. One briefing said the student "meets criterion 1". `check_output` caught neither.
- **Between rounds** (Bob task 10):
  - the guardrail was extended to block both kinds of statement;
  - `briefing_writer`'s instructions were tightened.
- **Round 2** ([`results/round2_review.md`](results/round2_review.md)):
  - No briefing makes an authorship statement or says a criterion is met.
  - Checked with the round-2 guardrail, round 1 has 10 of 18 briefings blocked and round 2 has none.
- **After round 2** (Bob task 11): a guardrail defect was fixed without a new model run. The new authorship rule had also blocked three questions that asked the student to answer "in your own words".

Problems that remain after round 2 (details in the round 2 review):

- One student question quotes words the student never wrote (S06).
- Two briefings accept a suggestion to replicate the study as a limitation.
- 6 of 93 evidence quotes are not word for word.
- One briefing labels each paragraph with a criterion and a confidence level.

The dummy backend's numbers only show that the pipeline works; its replies are deliberately generic.

## Importing into watsonx Orchestrate

Install the ADK (`pip install ibm-watsonx-orchestrate`, Python 3.11+; checked with version 2.19.1). In Orchestrate, open Settings → API details, copy the service instance URL and generate an API key. Then connect the CLI; it asks for the key at a prompt. Never put the key in a file or in a chat.

```bash
orchestrate env add -n viva-prep -u <service instance URL> --type ibm_iam --activate
DRY_RUN=1 bash scripts/import_orchestrate.sh   # prints the commands only
bash scripts/import_orchestrate.sh
```

`ibm_iam` is the authentication type for an IBM Cloud instance. The CLI would also infer it from a URL that contains `.cloud.ibm.com`.

The script builds `build/orchestrate_pkg/`. The package contains only `viva_prep/`, the course documents, the submissions, the agent files and a `.txt` copy of each course document, because ADK knowledge bases do not accept `.md`. It then imports the three tool files, the `course_knowledge` knowledge base, the four specialist agents and, last, `coordinator`. The answer key is never part of the package; a test checks this.

What the ADK source (version 2.19.1) shows, checked offline against the built package:

- The ADK's own loaders read all three tool files (7 tools) and the knowledge-base file without errors. The five agent files load once an `llm` field is added (see the last point; the offline check added it to temporary copies). Every tool, collaborator and knowledge base an agent names exists in the package.
- Document paths in a knowledge-base file resolve against that file's folder.
- An agent import stops if a tool, knowledge base or collaborator it names does not exist yet in the instance. The script imports them in that order, with `coordinator` last.
- The agent files have no `llm` field, so Orchestrate uses the instance's default model. If the instance has no default model, the import stops and asks for an `llm` field.

The import ran on the first attempt: 7 tools, the knowledge base and 5 agents. The agents use the instance's default model, `groq/openai/gpt-oss-120b`: the same model id as the batch runs, served through Groq instead of watsonx.ai. Orchestrate's sampling settings (for example the temperature) were not checked.

**Spot-check.** `question_planner` and `briefing_writer` were called directly through the ADK run API for three students: S01 (no planted misconception), S02 (one) and S10 (two). The results were scored with the same `evaluate.py` and are in `results/orchestrate_spotcheck/`. The tool calls and tool responses behind the statements in this section are in `results/orchestrate_spotcheck/trace/` (account fields removed). | Planted misconception named | 1/3 (rule-based) |
| Briefings ≤ 250 words | 3/3 (145–164 words) |

- Read by hand, 2 of the 3 misconceptions are named:
  - S02's briefing says the student treats the p-value as "how likely it is that the null hypothesis is correct". The M1 keyword rule ("probability", "null", "true") does not match this wording.
  - S10's briefing names M2 ("proves beyond reasonable doubt") but not M4, the claim that failing to reject the null would prove the two methods identical.
  - In both batch rounds, all three were named.
- Every quotation in the three briefings and their findings appears word for word in the submission (a quotation with "..." was checked piece by piece).
- In every call, `save_record` was called once and returned `"saved": false` with the note. No agent retried or returned "needs attention".

**Coordinator path.** One thread with `coordinator`, saved in `results/orchestrate_spotcheck/coordinator_S01.json`:

1. Start a round for S01 only.
2. Approve the question plan.
3. Ask for the briefing.

The coordinator called `list_submissions`, `get_round_status`, `question_planner`, `save_record` and `briefing_writer`, and ran `check_output` before each reply. Two problems:

- After the approval it told the instructor the plan was "approved and recorded", although `save_record` had returned `"saved": false`.
- When showing the briefing, it also listed the findings, each labelled with a rubric criterion and a confidence level. One label was the title of rubric criterion 5, "Clear reasoning in own words", placed next to a quote from the student. This is the same rubric wording that round 1's briefings turned into statements about authorship. `check_output` let it through:
  - its authorship rule needs a word such as "their" before "own words";
  - findings are not part of the batch "forbidden outputs" count.

Neither problem was fixed.

**Practice session.** The first Orchestrate run showed that `practice_partner` could not start: `get_approved_questions` finds no approved plan because nothing is saved, and the agent then stopped as instructed, even when the approved questions were given in the first message. Bob task 14 applied the fallback the project plan had set for this case:

- `practice_partner` uses the instructor-approved questions from the session-start message when `get_approved_questions` finds none;
- `practice_partner` is a collaborator of `coordinator`, which hands it the approved question texts only, and only when the instructor asks for a practice session.

Only the `coordinator` and `practice_partner` instructions changed. Neither agent is part of the batch evaluation. The three files the batch uses (`question_planner`, `briefing_writer`, `class_insights`) are unchanged, so their hashes in the round 2 `run_meta.json` still match.

## Known limitations

- **Records are not saved in Orchestrate.** Python tools in Orchestrate run on a read-only file system (confirmed in the first Orchestrate run). `save_record` then returns the record with `"saved": false`, `"reason": "store_not_writable"` and a note that this is expected and not a failed tool call. Without the note, the agents treated the unsaved record as a failed call, retried once and returned "needs attention". Practice sessions therefore start from questions passed in the conversation: the coordinator hands them to `practice_partner`, or they are pasted at the start of a direct chat (Bob task 14). The coordinator route worked in one run-API test and failed in a web UI rehearsal; the direct chat worked in every try. Practice Partner's separation from briefings then rests only on instructions, no longer on which tools it can reach, and a student in a direct chat could supply their own questions. Whether `practice_partner` sees earlier messages of the coordinator's conversation was not checked, so in the demo the practice session comes before any briefing is shown. In the first Orchestrate run, the coordinator still told the instructor that an approved plan was "recorded".
- **Measured on the same 18 synthetic submissions the prompts were tuned on.** The numbers are optimistic for unseen work.
- **Evaluation measures the "submission only" path.** That path covers all four targets. Full practice conversations are shown in the demo only.
- **Rule-based checks.** Misconception detection uses quotes and keyword sets, and `check_output` uses patterns. Both can miss a paraphrase or block an unusual but acceptable sentence.
  - In round 2, S18 names a misconception in words the keyword rule does not match. Read by hand, 22 of 24 misconceptions are named in both rounds; the official count stays 21/24 because the rules were not changed after seeing results.
- **The "forbidden outputs" target covers briefing text only.** Student questions and findings were checked separately for the reviews. In Orchestrate, each agent runs `check_output` on its own output. The coordinator also shows findings to the instructor, and one finding label ("Clear reasoning in own words") passed `check_output` in the first Orchestrate run.
- **Quotations are not checked against the submission.** No tool compares a quoted phrase with the student's text. This is how the invented quote in S06's question got through.
- **Two prompt rounds only**, as planned. The problems listed under Results and found in the first Orchestrate run were not fixed. The one later instruction change (Bob task 14) was the planned fallback for unsaved records and touched only `coordinator` and `practice_partner`, which the batch does not run.
- **Synthetic data only**, one course, one assignment, English only.
