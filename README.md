# Viva Prep

Viva Prep is a multi-agent assistant for IBM watsonx Orchestrate. It helps an instructor prepare short one-on-one conversations ("vivas") with students about their written work. Before a viva, students can practise with an agent. The instructor then receives a short briefing on each student, plus a class-level summary.

The project was built for the IBM SkillsBuild AI Experiential Learning Lab (Bring Your Own Challenge track). All data is synthetic: a fictional statistics course (STAT 110), a hypothesis-testing assignment and 18 fictional students (S01–S18). No real student data is used.

## What the agents do

| Agent | Talks to | Job |
|---|---|---|
| `coordinator` | instructor | Opens a round, asks `question_planner` for each student's questions, collects the instructor's approval or edits, asks `briefing_writer` and `class_insights` when needed. Never talks to students. |
| `question_planner` | (internal) | Writes 3–5 open questions per student. Each question quotes at least 6 consecutive words of the student's own submission. |
| `practice_partner` | student | Asks the approved questions one at a time, with at most 2 follow-ups per question. Never says whether an answer is right, never teaches the answer. It can only reach the approved questions (`get_approved_questions`), not briefings or notes. |
| `briefing_writer` | instructor | Writes a briefing of at most 250 words: what the student explained well, where the explanation broke down (quoting the student), and two suggested questions. Low-confidence points are phrased as "not sure — ask directly". |
| `class_insights` | instructor | Summarises the most common gaps across the round in at most 300 words, using student IDs only. |

Shared rules: no grades, scores or pass/fail verdicts; no statement or hint about whether the work was written by AI. Every text shown to a person first goes through `check_output` (a rule-based guardrail). Agents use only the submission, the rubric and the course knowledge base.

Each agent's behaviour is written once, in `prompts/<agent>.md`. The Orchestrate agent files in `agents/` are generated from these files. The batch evaluation reads the same files, so the evaluation tests the instructions used in the demo.

## Setup

Python 3.11 or later. The tools and scripts use only the standard library; pytest is needed for the tests.

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install pytest
pytest -q
```

## Measuring the success criteria

`scripts/run_batch.py` runs the "submission only" path for every student: `question_planner` writes the questions, `briefing_writer` writes the briefing, and the script runs `check_output` on each briefing. Each student's result is written to `results/run_<timestamp>/S##.json`, plus `CLASS.json` and `run_meta.json`; the meta file records the model id and a hash of every prompts file.

```bash
python scripts/run_batch.py --backend dummy          # offline, canned replies, used by the tests
python scripts/run_batch.py --backend watsonx --limit 2
python scripts/evaluate.py results/<run folder>
```

The `watsonx` backend calls the watsonx.ai chat endpoint (`/ml/v1/text/chat`). It reads `WATSONX_APIKEY`, `WATSONX_PROJECT_ID`, `WATSONX_URL` and `WATSONX_MODEL_ID` from the environment or from a local `.env` file, which is git-ignored; `.env.example` shows the format. The key and the token are never printed or written. The model is `openai/gpt-oss-120b`, the same model the Orchestrate agents use; it is listed as available for chat in the Dallas region (`us-south`).

`scripts/evaluate.py` checks four targets:

| Target | How it is measured |
|---|---|
| Questions tied to a specific passage ≥ 90% | a question counts if it contains a 6-word span from the submission, or 60% of its content words appear in one sentence of it |
| Planted misconception named ≥ 80% | the briefing quotes 6+ words of the evidence sentence, or contains the keyword set for that misconception (M5, "no assumptions or limitations", needs a negation and "assumption/limitation" in the same sentence) |
| Every briefing ≤ 250 words | 100% of briefings |
| Forbidden outputs = 0 | briefings blocked by `check_output` |

A student whose model call or reply parsing failed is marked `needs_attention`. It fails the first three targets and is reported on its own line.

**Results:** pending the first watsonx.ai run. All runs are kept in `results/`. The numbers from the dummy backend only show that the pipeline works; the dummy replies are deliberately generic.

## Importing into watsonx Orchestrate

Install the ADK (`pip install ibm-watsonx-orchestrate`, Python 3.11+; checked with version 2.19.1). In Orchestrate, open Settings → API details, copy the service instance URL and generate an API key. Then connect the CLI; it asks for the key at a prompt. Never put the key in a file or in a chat.

```bash
orchestrate env add -n viva-prep -u <service instance URL> --type ibm_iam --activate
DRY_RUN=1 bash scripts/import_orchestrate.sh   # prints the commands only
bash scripts/import_orchestrate.sh
```

`ibm_iam` is the authentication type for an IBM Cloud instance. The CLI would also infer it from a URL that contains `.cloud.ibm.com`.

The script builds `build/orchestrate_pkg/`. The package contains only `viva_prep/`, the course documents, the submissions, the agent files and a `.txt` copy of each course document, because ADK knowledge bases do not accept `.md`. It then imports the three tool files, the `course_knowledge` knowledge base, the four specialist agents and, last, `coordinator`. The answer key is never part of the package; a test checks this.

What the ADK source (version 2.19.1) shows, checked offline against the built package:

- The ADK's own loaders read all three tool files (7 tools) and the knowledge-base file without errors. The five agent files load once an `llm` field is added (see the last point; the offline check added it to temporary copies). Every tool, collaborator and knowledge base an agent names exists in the package.
- Document paths in a knowledge-base file resolve against that file's folder.
- An agent import stops if a tool, knowledge base or collaborator it names does not exist yet in the instance. The script imports them in that order, with `coordinator` last.
- The agent files have no `llm` field, so Orchestrate uses the instance's default model. If the instance has no default model, the import stops and asks for an `llm` field.

## Known limitations

- **Records may not persist in Orchestrate.** According to the ADK documentation, Python tools in Orchestrate run on a read-only file system. In that case `save_record` returns `{"error": "store_not_writable"}` instead of failing. The fallback is to run the demo in a single conversation, with the approved questions passed in that conversation. Practice Partner's separation from briefings then rests only on its instructions, no longer on which tools it can reach.
- **Measured on the same 18 synthetic submissions the prompts were tuned on.** The numbers are optimistic for unseen work.
- **Evaluation measures the "submission only" path.** That path covers all four targets. Full practice conversations are shown in the demo only.
- **Rule-based checks.** Misconception detection uses quotes and keyword sets, and `check_output` uses patterns. Both can miss a paraphrase or block an unusual but acceptable sentence.
- **Synthetic data only**, one course, one assignment, English only.
